# Harness 工程规范

> 阶段 1 就位时读「五角色 / 五道门禁」；阶段 3 每个 feature 过门禁时读各纪律节；阶段 5 读「发版评审会」。产出：流程就位 → 过门禁的 feature → 评审结论。

> 阶段 1 就位、阶段 3 迭代实施时读取。用户无需懂这些，你自动执行。

## 五个角色，各管各的

让项目不乱的核心：**写代码的人不能同时是检查代码的人。**

| 角色 | 只做什么 | 不做什么 |
|------|----------|----------|
| 架构师 | 出设计文档 | 不写一行代码 |
| 开发者 | 按设计写代码 | 不改设计、不自测 |
| 测试员 | 写测试案例、跑测试 | 不修 bug，报告给开发者修 |
| 审查员 | 查架构合规 | 不改代码 |
| 调度员 | 路由任务、更新进度 | 不管业务 |

**降级说明**：如果当前宿主不支持子智能体（多 Agent 并行），就由你一个人在会话里「按角色切换」严格执行——关键检查一样不少，只是串行完成。不要让用户操心这件事。

## 文件交接

每个角色干完活，把产出写进 `phases/` 文件夹，不靠聊天记录交接、靠文件：

```text
架构师 → phases/01-design.md
    ↓ 开发者读这个文件
开发者 → 代码 + phases/02-impl.md
    ↓ 测试员读这个文件
测试员 → phases/03-test.md
    ↓ 审查员读这个文件
审查员 → phases/04-review.md
    ↓ 调度员判断能否完成
```

每次新会话打开文件就知道做到哪了。

## 五道门禁

每步干完必须通过检查，不通过不许往下走：

| 门禁 | 检查什么 | 谁查 |
|------|----------|------|
| Gate 0 | 需求说清楚了吗？ | 架构师 |
| Gate 1 | 设计文档完整吗？ | 调度员 |
| Gate 2 | 代码能编译吗？ | 开发者 |
| Gate 3 | 测试全过了吗？ | 测试员 |
| Gate 4 | 架构违规了吗？越界了吗？ | 审查员 |

## Gate 4 越界检查（审查员必做）

审查员开工前，先对照该 feature 声明的改动范围（`phases/02-impl.md` 里写的）列出实际改动的文件：

- **范围内的** → 正常走架构合规审查
- **超出范围的** → 逐个确认：确实必要的向用户说明理由；顺手发散的（改了没让改的、重构没坏的部分、加没要的功能）列为阻塞问题

采集方式：`git diff --stat` 对照声明范围，检查结论写进 `phases/04-review.md`。

## 五类失控检查（审查员必查，防 AI 越写越乱）

AI 长期开发会自然滑向五类失控，审查员每个 feature 审查时逐类过：

| 失控 | 查什么 |
|---|---|
| 样式碎片化 | 同类 UI 是否复用统一组件/样式，颜色/间距是否来自同一份设计清单（见 [yy-polish](../yy-polish/SKILL.md) 设计一致性） |
| 硬编码泛滥 | 数值、路径、尺寸是否抽成了变量或配置；直接写死的关键参数列为阻塞问题 |
| 重复造轮 | 新代码是否重写了已有函数/组件——写之前先查已有实现（`git grep` / 项目索引），确认无现成的才写新的 |
| 冗余残留 | 旧逻辑的 fallback 兜底代码是否清干净——改完即删，不留「以防万一」的历史残留 |
| 文档过期 | 本 feature 改动后，立项文档（功能清单/架构）是否同步更新、过时描述是否删除 |

## 测试节奏分层（不把时间浪费在等测试上）

| 时机 | 跑什么 | 不跑什么 |
|---|---|---|
| 编码途中 | 秒级检查：语法、lint、类型 | 全量测试、构建 |
| feature 做完 | 该功能相关的快测 | 全量回归 |
| 发版评审前 | 全量回归 + 构建统一跑一次 | —— |

执行 Agent 自报「快测通过」不算数，调度员亲自跑一次核实。

人机分工：复杂交互与体验类测试交人工点验；性能压测、火焰图这类数据密集任务全权交 AI；高频调试链路封装成脚本或参数化测试，不一遍遍手动重复。

## 修 bug 的固定路径

1. **先复现**：写一个会失败的测试（能写就写），确认它真的失败，再动手修
2. **修根因**：在坏数据产生的地方修，不在报错的地方挡症状
3. **验收**：同一个用例转绿才算修好；测试员不修 bug，只报告给开发者
4. **止损**：同一个 bug 连续 2 轮修复失败 → 停下来重估——换思路、简化需求或向用户报告选项，不闷头做第三次同样尝试

## 多模型交叉评审（可选增强）

宿主有多个模型/子智能体可用时：方案由表达力强的模型写、防御性强的模型挑风险补盲区；疑难 bug 让第二个模型独立诊断根因，两边结论一致再动手。单人宿主不降级为「随便看看」——由五角色分次自审代替（写方案的自己 ≠ 挑刺的自己）。

## 防三个经典翻车

| 翻车 | 怎么防 |
|------|--------|
| 「帮我开发一个系统」——AI 一次想做太多 | 每次只做一个 feature，拆成独立小任务，做完一个再下一个 |
| 代码写完了就当完成了 | 五道门禁全过才算完成 |
| AI 写的测试和 AI 写的代码有同样盲区 | 测试员和开发者不能是同一个角色 |

## 代码质量重点

**后端**：服务可启动、配置可加载、接口返回格式统一、错误处理机制、日志规范、数据库连接与权限入口。

**前端**：目录结构分层合理、组件命名与复用规范、请求封装统一、状态管理策略明确。

**通用**：关键参数（数值、路径、尺寸）抽离为变量或配置；写新代码前先查已有实现，有现成的不重写。

## Harness 思想（始终遵循）

1. 任务分流、分布，避免死循环
2. 任务满足要求才可输出
3. 兜底机制
4. 成长维护，保证 agent 健康运行

## 发版评审会（可选，发版前）

项目准备发版（发布/上线）前，先问用户「是否需要发版评审会？」，由用户决定。

用户说需要 → 进入评审会流程：

1. 设置多个评审角色（如架构评审、代码评审、产品评审、安全评审、体验评审）+ 一个「集成评估师」。
2. 各角色对候选版本**互相挑刺、质疑**，找出问题。
3. team leader（总调度）**不参与辩论**，只做最终敲定。
4. 集成评估师汇总各方意见，形成结论：**可以发版 / 需要修改**。
5. 结论「可以发版」才进入部署/发布；「需要修改」则回到对应阶段修复，修复后重新评审。

**降级说明**：宿主不支持多角色并行时，由你一人依次扮演各评审角色，但「集成评估师」的汇总和「team leader」的敲定要分开做，不能自己评审自己敲定。

## 发版四卡点（硬约束，缺一不发版）

不管用户是否选择开评审会，发版前这四项必须逐项确认：

1. **版本号已更新**（项目里的版本位置，含对外页面）
2. **CHANGELOG 已写**（本版改了什么，一句话一条）
3. **全量测试绿**（发版评审前那次全量回归的结论）
4. **回滚方案一句话**（出问题怎么退回去）

能写成 CI 脚本或检查命令的写成脚本硬拦，不靠自觉。
