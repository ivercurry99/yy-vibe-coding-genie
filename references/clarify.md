# 子技能：阶段 0 —— 需求明确（动手前必做）

> 何时读：收到项目信息、准备开工时。
> 产出：7 份立项文档 + 《需求确认单》。
> 停止点：用户确认需求单后，才退出计划模式进入阶段 1。

想法粗糙时，**不要直接写代码**。宿主支持计划模式（Plan mode）时，**默认先进入计划模式**——只澄清需求，不实施。按固定顺序走：

1. **进入计划模式**：告诉用户「先在计划模式下把需求聊清楚，你确认后我才动手」。
2. **把需求澄清技能真正调起来**（本阶段优先级最高的一步）：
   - 查宿主技能列表：有 `brainstorming`（superpowers 头脑风暴）或 `grill me` 任一 → 直接调用，把项目描述传入；
   - 都没有 → **先安装再调用**：`npx skills add obra/superpowers`，或用宿主自带的技能市场安装；
   - 宿主不支持安装/调用技能 → 降级为等价开放式提问（见 [fallback-strategy.md](fallback-strategy.md)），并写明一行：「需求澄清方式：等价开放式提问（未调用 brainstorming / grill me，原因：未安装且无法安装 / 调用失败）」。没写这行声明，等于没做需求澄清。
3. **GitHub 方案调研（写技术选型前必做）**：用 GitHub / 网络搜索能力，按「核心模块关键词 + awesome 清单」找 2-3 个可复用的开源项目，记录名称、链接、可复用点。明确写过「从零写」的模块才允许从零写。宿主无网络能力 → 写明「本次未做 GitHub 调研（宿主无网络能力），选型基于本地常识，需人工核对」再继续。
4. **产出 7 份文档 + 《需求确认单》**：目标用户、核心价值、功能边界、风格偏好四项有明确答案；调研结果写进技术选型文档的「复用参考」节。请用户确认。
5. **UI 路由询问（项目涉及网页/界面/前端时必问）**：向用户说明并询问——
   > 「检测到这个项目有 UI/前端页面。要不要调用 `yy-ui-first-webgen` 技能做视觉定稿？它会在写代码之前：① 把 UI 设计提示词具体化（色值/布局/组件规格），② 生成 UI 效果图给你确认（无生图能力时用文字版设计规格书代替），③ 拆好需要的图片素材，然后再进入开发。好处是还原度高、返工少。」
   用户同意 → 调用该技能，完成视觉定稿后回到本流程；用户拒绝或项目无 UI → 直接进入阶段 1，不强推、不重复追问。
6. **用户确认后退出计划模式**，进入阶段 1。

## 7 份立项文档

立项说明、功能清单、项目管理档案、推进计划、技术栈选型、项目架构、项目级工程规范。按工业级标准。有新想法自己定，但先告诉用户确认，不擅自扩大范围。

## 本阶段红线

- 没写降级声明 = 没做需求澄清；没写调研声明 = 没做 GitHub 调研
- 明确写过「从零写」的模块才允许从零写
- 功能清单要写「本期不做」边界，防止范围越做越大
